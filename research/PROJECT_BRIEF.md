# VBCUA — Project Brief

*Voice-Based Concept Understanding Analyser.* Factual brief for writing the report, slides and talk.
Sources: the repository, git history, `vbcua.db`, `research/results/` and
`VBCUA_Documents/Research Plan/VBCUA_Work_and_8-Week_Plan.pdf`. Snapshot: **12 Oct 2026, morning** (first written 11 Oct).
Anything not established in those sources is marked **TBD**.

---

## 1. Summary

VBCUA is a web app in which a student records a spoken explanation of a computer-science concept and gets
an automatic assessment: a transcript, an understanding score, a delivery score, AI-written feedback and a
PDF report, with every attempt saved. **The problem:** students preparing for viva voce, presentations and
technical interviews cannot easily tell whether their spoken explanation is correct and complete, and
faculty cannot give every student detailed oral feedback. **Who it's for:** undergraduate CS students
practising explanations, and the faculty who coach them. It began as a solo final-year project (built June
2026) and is now being turned into a short research paper on whether its scores can be trusted.

## 2. Original project (June 2026)

**Built solo in June 2026**; first commit in this repository is `383f802` (13 Jul 2026).

| Area | Original implementation |
|---|---|
| Frontend | Streamlit dashboard (record in browser or upload .wav/.mp3/.m4a, waveform preview) |
| Backend | FastAPI, 7 REST endpoints + health check; SQLAlchemy; PostgreSQL or SQLite |
| Speech-to-text | Google Gemini first, OpenAI Whisper as local fallback |
| Understanding | Sentence-BERT `all-MiniLM-L6-v2` cosine to a reference definition + keyword check |
| Delivery | Librosa: filler-word rate, pause ratio, speaking volume (RMS) |
| Scoring | Understanding, fluency, overall; grade Strong (≥80) / Moderate (≥50) / Poor |
| Feedback | Gemini (`gemini-1.5-flash`, `google-generativeai` SDK); rule-based fallback |
| Other | Concept library (3 seeded: ML, Cloud Computing, DBMS), history, PDF report (ReportLab), `run.py` launcher |
| Documents | Ideation, requirements, design, planning, testing reports, project report, demo videos (`VBCUA_Documents/`) |

**Architecture:** Streamlit → FastAPI → five-stage pipeline (transcribe → audio features → semantic score →
fluency score → feedback) → database → PDF on request.

**What was wrong (the 10 known problems, in plain words):**

1. The similarity score could never fall much below 50, because cosine was rescaled as (cos + 1)/2, so an
   unrelated answer still looked half-right.
2. Gemini was tried before Whisper, so you could not tell which system produced a transcript.
3. The Gemini model and SDK used had been retired, so AI calls failed and silently fell back.
4. The "volume" score measured the microphone, not the speaker.
5. Filler words ("um", "uh") were counted on transcripts that speech recognisers clean, so the counts were
   near zero and meaningless.
6. Keyword matching accepted substrings ("data" matched "database").
7. Sub-scores were not stored, so results could not be re-analysed.
8. The frontend recomputed fluency itself and could show the wrong concept's badges.
9. User text was inserted into HTML and the PDF without escaping.
10. The documents described features (login, extra endpoints, test results) not in the code.

## 4. Current app

**Architecture:** React web app (browser) → FastAPI (`backend/app/main.py`, 11 API endpoints + the web app) →
services (`speech_to_text`, `audio_analysis`, `semantic`, `evaluation`, `llm_client`, `discover`,
`pdf_report`) → SQLite `vbcua.db` (tables `reference_concepts`, `evaluations`, `trending_topics`).

**Scoring pipeline per attempt (`POST /api/evaluate`):**

| Step | What happens | Model / formula |
|---|---|---|
| 1. ASR | Transcribe the recording | Local Whisper `small` (CPU), English; Gemini fallback off by default |
| 2. Audio features | Pause ratio (edge silence trimmed), duration, RMS (warning only), fillers (stored, experimental), speaking rate, long pauses | Librosa |
| 3. Understanding | Cosine to the concept's reference description; keyword coverage | `all-MiniLM-L6-v2`; similarity = max(0, cos)×100; **understanding = 0.7 × similarity + 0.3 × keyword coverage** |
| 4. Rubric grader | **Not in the app yet** — research code only (`research/asag/grader.py`) | `gemini-3.8-flash` (research) |
| 5. Fluency (provisional) | Pause ratio only: −(ratio−0.30)×100 (max 25) if >0.30; −10 if <0.05; floor 10 | v1 |
| 6. Overall + grade | **final = 0.7 × understanding + 0.3 × fluency**; Strong ≥ 80, Moderate ≥ 50, else Poor (cut-offs uncalibrated) | — |
| 7. Feedback | Rule-based at once; AI feedback on request (`POST /api/evaluations/{id}/feedback`) | `gemini-3.5-flash-lite` |
| 8. Report | PDF per attempt | ReportLab |

Topic discovery uses `gemini-3.5-flash-lite` with Google Search grounding (cached daily, curated fallback).

**Stored per attempt (35 columns):** transcript; ASR model, confidence, device; similarity, cosine, keyword
coverage, mentioned/missing keywords, understanding score, semantic method; filler count/ratio, pause ratio
(raw and v1), RMS, duration; speaking rate, long-pause count/rate, longest pause; fluency score and method;
final score, grade; feedback, source, LLM model, status and timing; audio path; timestamp.

## 5. Research design

| RQ | Question |
|---|---|
| RQ1 Accuracy | Does rubric-based LLM scoring (key points + misconceptions) agree with human ratings better than the Sentence-BERT cosine score? |
| RQ2 Robustness | How much do speech-recognition errors (Whisper tiny/base/small, accent, noise) change the scores? |
| Later (optional, from the plan) | Does hesitation predict wrong answers; adaptive follow-up viva questions; a feedback study with a class — TBD |

**Datasets**

| Dataset | Details | Status |
|---|---|---|
| Mohler et al. (2011) | 2,273 answers to 81 open-ended questions, introductory data-structures course, Univ. of North Texas; two graders, 0–5 (`score_avg` mean 4.18). No licence stated by authors; cite the ACL 2011 paper. Obtained via Hugging Face `nkazi/MohlerASAG` (cleaned, open_ended). Kept git-ignored, not redistributed | **In use (pilot dataset)**. Sample 300 → 100 dev / 200 test |
| EngSAF (Aggarwal et al., AIED 2025) | ~5.8k engineering short answers, 3 labels; access by request only, no redistribution | **Requested 11 Oct 2026**; pipeline ready. If no access by 18 Oct, Mohler stays the pilot |
| Self-recordings | 6 concepts × 5 (good1, good2, partial1, partial2, wrong1), 60–90 s; hand-rated before scoring; approved reference answers | **30 planned, 0 recorded**; checklist and rating sheet ready; target 17 Oct |
| Student recordings | Plan: 15–20 students × 6 concepts (~150 clips), ethics approval, second rater on 30% | **TBD** |

**Methods compared:** **B0** — original cosine (cos + 1)/2 × 100; **v1** — max(0, cos) × 100; **rubric LLM grader** —
per key point 0/1/2 plus misconceptions, score = max(0, Σ marks − misconceptions stated) / (2 × key points) × 100.

**Rubrics:** dataset rubrics generated by Gemini **from the question and reference answer only** (1–6 key points,
1–3 misconceptions). Six concept rubrics hand-drafted for the app (`research/rubrics/`), **DRAFT – NOT FACULTY
REVIEWED**, with a review document for a faculty member.

**Leakage and bias protections**

- Stratified sample (label, then question), seed 42; dev/test split fixed **before** any scoring and never re-drawn.
- Everything fitted (label cut-offs, linear map to 0–5) uses **dev only**; all metrics reported on **test only**;
  a test checks that changing test labels does not change the fit.
- Rubric generation sees no student answers or labels (enforced by the function signature).
- **Verbatim-evidence rule:** a key-point mark > 0 or a misconception counts only if the grader quotes the answer word for word.
- Every Gemini answer cached on disk keyed by (model, prompt hash), temperature 0; call budget per run.
- Grader prompt treats answers as data; answers in a batch are shuffled (fixed seed) and labelled A1, A2, …
- Self-recordings: hand ratings frozen with a checksum before scoring; reference answers approved and checksummed (`cc5cafe`).

**Metrics:** Pearson, Spearman, RMSE vs `score_avg` (primary on Mohler); QWK, Spearman, accuracy on 3 labels
(< 2.5 / < 4.5 / ≥ 4.5; secondary); 95% bootstrap CIs (1,000 resamples, seed 42); human ceiling = grader 1 vs grader 2.

**RQ2 synthetic speech**

| Factor | Levels |
|---|---|
| Text | The 200 Mohler test answers (mean 20 words) |
| Voices (Piper TTS, offline) | Indian English: L2-ARCTIC speaker **TNI** (Hindi L1, chosen by ear from 4 before any transcription); British `alba`; US `ryan` |
| Noise | Clean; DEMAND cafeteria noise at **20 dB** and **5 dB** SNR |
| ASR | Whisper tiny, base, small (as the app runs it) |
| Conditions | 3 × 3 × 3 = **27**; 1,800 transcriptions per model (5,400 total) |
| Scoring | Cosine (v1, B0) + WER on all; rubric grader only on Indian × heavy noise × tiny and small |

**Free-tier constraint and batching:** the Gemini free tier allows **20 requests/day** for `gemini-3.8-flash`.
Calls are batched: rubrics 10 questions per call (9 calls), grading one call per question with all its sampled
answers (81 calls), plus a **batching check** — 10 fixed dev answers re-graded one per call (10 calls) to measure
whether batching changes scores. Main run **100 calls**; RQ2 **162**; self-recordings **6**; total **268** (~14 days of quota).

## 8. Limitations and risks

- **Synthetic speech** has no hesitations or self-corrections and a milder accent than real students, so RQ2 likely understates ASR errors.
- **Single Indian-English speaker** (TNI), single noise type (cafeteria); self-recordings from one speaker (the author).
- **Mohler** is from 2011, US, one course, skewed to correct answers (63% "correct" label); widely published, so possible LLM training-data contamination.
- **Human ceiling is modest** (r = 0.56), which caps any method's measurable agreement.
- **Free-tier pace** (20 calls/day) stretches the LLM work over ~14 days; quota errors stop runs.
- **Gemini free tier** may use submitted content to improve Google's products (disclosed in the EngSAF request).
- **Grade cut-offs (80/50) uncalibrated** after removing the similarity floor.
- **Fluency is provisional** (pause ratio only, few distinct values); delivery scoring deferred.
- **Rubrics** are drafts, not faculty reviewed; LLM-generated dataset rubrics may miss or invent points.
- **Batching** could bias grades (measured by the 10-answer batching check).

## 11. Talking points

1. **VBCUA listens to a student explain a concept and tells them how well they understood it** — like a practice viva that never gets tired.
2. **The old score could be fooled:** an answer that merely *sounds like* the topic scored well. We fixed the maths and now test the scores against real teachers' grades.
3. **We are testing a "checklist" grader:** instead of "how similar is this to the textbook?", an AI checks each key idea and common mistake, and must quote the student's own words as proof.
4. **Fair testing:** the questions used to tune the system are kept separate from those used to judge it, and every AI answer is saved so results can be checked and repeated.
5. **Accents and noise matter:** we play the same answers in Indian, British and US voices, with café noise, through three sizes of speech recogniser, to see how much mistakes in hearing change the score.

**Example (from the app's own history, attempt 3, Machine Learning):** a vague explanation ("machine learning is
nothing but a part of artificial intelligence…") scored **73.3% similarity** to the reference but **0% of the
key terms**, giving understanding 51.3 and an overall **64.4 — "Moderate Understanding"**. In another attempt
(attempt 1), a talk about **DBMS** checked against the **Cloud Computing** concept still scored **51.5, "Moderate"**.
Similarity alone rewards sounding on-topic; that is what the rubric grader is meant to fix.
